# TaskVault — project instructions

**TaskVault** (formerly Lowbid: the code, settings and static files keep the `lowbid` / `LOWBID_` / `Lowbid` prefix) is a task board for freelancers on Stellar (Hack Meridian, track *Composed*). A company splits a project into **tasks with a budget** (`Task.budget`, the maximum; `Task.price` starts equal to it and is the amount that moves). Freelances apply to a task with **their own price** (`Application.price` ≤ the budget, `over_budget` otherwise), a message and their skills. The company picks one freelance per task, with a deterministic score as a hint (the price never enters the score); `choose` copies the chosen price onto `Task.price` (`Task.budget` is untouched and shown as « up to … » beside the agreed price), so everything downstream (escrow, payment, totals) moves that amount. The chosen freelance delivers a link, the company validates and rates the delivery (1–5) — or, in escrow mode, a party opens an on-chain dispute that an arbiter wallet settles with a split —, and the task's price is released in **USDC from a Trustless Work escrow on Soroban**: one single-release escrow **per task**, deployed and funded once the freelance is chosen. The fallback is a direct USDC payment at validation. The payment asset can be configured. UI copy, code, docs and commits are **English** (URL paths stay French: `/projets/`, `/taches/`, …).

There is **no GSD workflow** in this repo. Edit files directly, run `make check`, commit.

## Stack

- Python 3.13 · Django 5.2 (server-rendered templates, function views, no DRF) · SQLite by default (`data/db.sqlite3`, moved by `LOWBID_SQLITE_PATH`), PostgreSQL when `DJANGO_DB_HOST` is set · whitenoise for static files · gunicorn in Docker.
- Frontend: **self-hosted Tailwind v3** compiled into the committed `static/css/tailwind.css`, two hand-written CSS files (`lowbid-tokens.css`, `lowbid-components.css`), vanilla JS (`static/js/lowbid-*.js`). Vendored under `static/vendor/`: Font Awesome, `@stellar/freighter-api` (global `freighterApi`), `@stellar/stellar-sdk` (global `StellarSdk`), anime.js v4 (`anime.umd.min.js`, global `anime`, landing only). **Nothing loads from a CDN.**
- Stellar: the Freighter wallet is the identity (SEP-53 `signMessage` login). The payment asset is `STELLAR_ASSET_CODE` / `STELLAR_ASSET_ISSUER` (default: Circle testnet USDC; `XLM` with an empty issuer means native XLM, which forces direct mode). Trustless Work v1 REST runs the escrow; Horizon serves balances, trustlines and direct payments. Python side: `stellar-sdk`.
- Tests: Django test runner (`manage.py test`, 531 tests, network mocked) and a Playwright e2e run with a simulated Freighter and a fake Horizon (`make e2e`). Linter: ruff (baseline rules only, see `ruff.toml`).

```bash

make check      # lint + test + css-check — run before every commit
make seed       # python manage.py seed_demo --flush (5 wallets incl. the arbiter and freelancer C, 3 projects + a small trust network: the pitch state, a draft, and a food-truck project with a task delivered again after a change request + a disputed escrow task; with deposits active the pitch and food-truck projects hold a funded deposit, the draft is unpublished and a 4th, cancelled bakery project shows a forfeited deposit on `/fonds/`)

make fmt        # ruff check --fix .
make run        # runserver $(HOST):$(PORT) (default 0.0.0.0:8000), no migrate
npm run build:css / npm run watch:css / npm run vendor
```

`PY` is detected (python3.13, else python3.14, else python3; override with `make PY=…`). `.env` is read once at boot (python-dotenv): restart `make run` after any change. `DJANGO_DEBUG=0` requires `DJANGO_SECRET_KEY` (and running `manage.py` without a `.env` falls back to `DEBUG=0`, so set `DJANGO_DEBUG=1` or create `.env` first).

**Asset cache rule:** static files are served with a 30-day `max-age` outside DEBUG and cache-busted only by `?v={{ LOWBID_ASSET_VERSION }}`. After editing any `static/css/lowbid-*.css` or `static/js/lowbid-*.js`, bump `LOWBID_ASSET_VERSION` (default in `lowbid/settings.py`, override in `.env`).

## Conventions

- 4-space, `snake_case`, type hints where cheap, `logger = logging.getLogger(__name__)`, structured `level=… logger=… msg=…` logs on stdout. No `print()`.
- Broad `except Exception` only around network hops **and always with `logger.exception(...)`**. Never a silent `except: pass`.
- Business rules live in `<app>/services.py` and raise `ProjectError` / `PaymentError(code, message)`; views only map codes to HTTP (`ERROR_STATUS` in `projects/views.py`); templates never decide a rule.
- `projects/services.py` never imports `payments` at module level (`payments.services` imports it, so its hooks import `payments.services` lazily); views may import both. `payments` owns everything on chain; `projects.services.mark_paid(task)` is the **only** way a task becomes `paid`.
- Unsafe browser calls go through `Lowbid.api(url, {method:"POST", body})` (CSRF + JSON + `X-Requested-With: fetch`, so `wallet_required` answers 401 JSON instead of redirecting). Business refusals from `/pay/` are HTTP 200 `{ok:false, error, message}`; from projects they are 4xx with the same body.
- Money is `Decimal(18,7)`; format with `{{ x|usdc }}` (unit = the configured asset) / `Lowbid.formatUsdc`; data attributes use `{{ x|plain }}` / `dec_str()` (never `'4.5E+2'`).
- Migrations are committed (`makemigrations --check` in CI). `WalletUser` FKs use `on_delete=PROTECT`.
- Config only via env / `.env` (`.env.example` lists everything). Never hardcode hosts, secrets, colours or the asset.

## Payments

The escrow / direct-payment state table (who signs, Escrow status, Task status, on-chain call per step) is the docstring of `payments/services.py` and the **Payments** section of `docs/ARCHITECTURE.md`. Summary: escrow mode = company `deploy` + `fund` once a freelance is chosen (« Fund the project » chains both for every assigned task) → freelance `deliver` (milestone change, link as evidence) → company validates + rates (DB) → company `approve` + `release` (chained). Direct mode = freelance delivers (no transaction) → company validates + rates → company `direct_pay`. Review window: after a delivery the company has `LOWBID_REVIEW_DAYS` days (deadline computed at read time) to validate or to `request_changes` (max `LOWBID_MAX_REVISIONS`, before the Rating): task `delivered → taken`, Escrow `delivered → funded` | `created` through `payments.services.on_changes_requested`, the freelance delivers again (a second milestone change; a replay of the old XDR is `tampered`). Every delivery is a `Delivery` row, every request a `RevisionRequest` row; the fingerprint (`delivery_hash`) goes on chain inside the milestone evidence, and the full deliverable (`source_link`) is revealed to the company only once the task is paid or resolved (`source_visible`). `projects` owns `open → taken → delivered`; `payments` confirms on chain and calls `projects.services.mark_paid` (`delivered → paid`), and moves the project `draft → funded` (`mark_paid` closes it once every task is paid or resolved). Dispute (escrow mode only): the company (delivered, unrated) or the freelance (review window over) signs `dispute` (reason kept in the DB — Trustless Work `dispute-escrow` has no reason field) → Escrow + Task `disputed`, a `Dispute` row → the arbiter wallet (`LOWBID_DISPUTE_RESOLVER`, default the platform address, stored as the escrow's `resolver_address` / `disputeResolver`) signs `resolve` on `/litiges/` with `freelance_pct` (balance read on chain, addresses from the Escrow row) → `projects.services.mark_resolved` (the only gate to `resolved`; settled, not paid). Direct mode has no dispute (`wrong_mode`, `[data-direct-warning]`). **Publication deposit** (escrow mode + `LOWBID_DEPOSIT_ENABLED` + the three server settings, else inactive and the project is published at creation): the company signs deploy + fund of a project-level escrow (max(1 % of the budget, 5 USDC); receiver = company, platform key = approver / serviceProvider / releaseSigner, a second server key = disputeResolver) before `/projets/` lists the project and before `apply` accepts (`not_published`, `not_covered` for tasks added beyond the covered budget until a top-up); `deposit_verdict` (pure, read at request time) says refund / forfeit / locked; refund = milestone + approve + release and forfeit = dispute + resolve 100 % to `LOWBID_GUARANTEE_FUND_ADDRESS`, both signed by the server inside one request (TW XDRs live about a minute), triggered by the commit that closes / cancels the project or by « Reclaim my deposit » / « Report a ghost listing »; `/fonds/` is public. Secrets never reach logs, templates or JSON. Fallback switch: `LOWBID_PAYMENT_MODE=direct` + restart (a native-XLM asset forces it).

## How to add a page (5 steps)

1. View in `<app>/views.py` (function view, `@wallet_required` if it needs a session, `get_wallet(request)` for the caller), rules in `services.py`.
2. Route in `<app>/urls.py` under its namespace; add it to `NAV_LINKS` in `core/context_processors.py` if it belongs in the navbar / tab bar.
3. Template extends `base.html` (blocks: `title`, `meta_description`, `extra_head`, `body_class`, `content`, `extra_js`); start with `{% include "partials/page_header.html" with title=… subtitle=… %}` and compose with `templates/components/*`.
4. Page JS goes in `static/js/` (then bump `LOWBID_ASSET_VERSION`); new Tailwind classes → `npm run build:css` and commit `tailwind.css`.
5. Tests in `<app>/tests.py` (status code, key strings, role gates) and `make check`.

## Don'ts

- No CDN, no web fonts (system stack), no new JS framework, no SPA, no DRF, no Channels / WebSockets (the task page polls `candidats.json` every 5 s through `Lowbid.poll`).
- No silent `except`, no `print()`, no hardcoded colours / hosts / secrets / asset.
- No `window.confirm` / `alert` — `Lowbid.confirm` / `Lowbid.toast`.
- No business rule in a view or a template.
- Never flip `Task.status` to `paid` outside `projects.services.mark_paid`, and never move money from `projects`.
- Never commit `static/css/tailwind.css` out of sync with the templates, and never edit it by hand.
- The trust-network badge never changes the score or the candidate order, and is never the bare word "Recommended" (it always names someone: "Yanis recommends").
- No cron or background worker: every state change happens in a request (there is no timer anywhere in the task board).
